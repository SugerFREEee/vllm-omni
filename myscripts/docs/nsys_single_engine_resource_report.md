## 推理前 / 推理中 / 推理后 总结
- 推理前：GPU 计算几乎空闲，显存基线 ~1.292 GB，SM/GR 利用率 ~0%。
- 推理中：显存峰值 ~1.47 GB；窗口内 占用% 常在 70–95%，单窗口 SM/GR 均值多数在 56–95%，但“整体平均”仅 25–32%，主要被窗口间空档和同步拖低；同步 API 占 runtime ~46%。
- 推理后：GPU 回落到空闲，计数器与显存无额外占用（未观察到持续占用增加）。

## 建议
1) 若要提升单进程吞吐：减少 `cudaStreamSynchronize` 频率（批量化、减少队列 flush），或增加 kernel overlap（多流/算子融合），同时关注内存占用上限 ~1.47 GB。  
2) 计数器采样粒度与空档影响平均值，必要时结合时间线查看空洞（长同步/间隙）并优化调度。  
3) 理论并行数：单窗口 占用% 已 70–95%，单窗口内部追加并行收益有限；但全局 占用% 仅 ~31%（窗口间有空档），可在时间上并行 3 个左右的推理填满空档、提升吞吐（需接受延迟上升）。  
4) 如果要挖掘窗口内余量：优先检查 SM/GR 均值低于 ~70% 的窗口（如 56–68% 的几个窗口），尝试微批/多流，但要盯显存（峰值 ~1.47 GB）和带宽。  
5) 继续保留 NVTX 标注，便于按推理窗口分段分析；如需多进程对比，可复用本 SQL 模板批处理不同 `.sqlite`。
6) 关于“窗口 占用% 高但 SM/GR 平均低，是否可以在单窗口并行多个请求”：  
   - 计数器是采样平均，窗口内短暂空洞/同步会拉低平均；峰值已到 100%，说明有时刻满载。  
   - kernel 可能未占满 SM（小 kernel/warp 少），时间被填满但硬件利用率不高。  
   - 窗口内再叠加请求收益有限，除非确认 kernel 不饱和且显存/带宽允许；建议先用多流/微批小幅并行，监控显存（峰值 ~1.47 GB）与同步开销，并接受延迟上升。  
   - 若需更精准判断，按窗口对 SM/GR 计数器做分段统计（当前为整体平均），看单窗口平均是否仍明显低于 70–80%。
